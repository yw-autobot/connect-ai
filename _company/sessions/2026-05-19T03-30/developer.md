## 🏗️ [1단계] 기술 구조 분석 및 결정 (The Architecture)

**결론:** Headless Commerce는 필수적이며, 핵심은 **프레젠테이션 계층(Next.js)**과 **데이터/비즈니스 로직 계층(Shopify API + Strapi)**을 철저히 분리하는 것입니다.

| 구성 요소 | 역할 (WHY) | 최적 기술 스택 | 코다리 분석 및 리스크 관리 |
| :--- | :--- | :--- | :--- |
| **프론트엔드** (UX/SEO) | 사용자에게 노출되는 모든 인터페이스를 담당. SEO, 로딩 속도(TTFB)가 생명. | **Next.js (React)** | SSR 및 SSG 기능을 활용하여 검색 엔진 최적화를 극대화합니다. 클라이언트 측 상태 관리는 Zustand나 Recoil 같은 경량 라이브러리로 관리하는 것이 좋습니다. |
| **CMS/데이터 레이어** (콘텐츠) | 상품의 설명, 블로그 글 등 비즈니스 로직이 아닌 '콘텐츠'를 관리. 마케팅팀의 빠른 수정 대응력 확보. | **Strapi 또는 Contentful** | 상품 메타 정보(색상별 상세 스펙, 에디토리얼 콘텐츠) 관리에 최적입니다. *주의:* 재고/가격 변동 등 실시간 비즈니스 로직은 CMS가 아닌 커머스 엔진에서 가져와야 합니다. |
| **커머스 엔진** (트랜잭션) | 재고 관리(Inventory), 가격 책정, 주문 처리, 결제 게이트웨이 연동 등 핵심 트랜잭션을 전담. | **Shopify API** (혹은 Commercetools) | 복잡한 이커머스 로직을 직접 구현하는 것은 리스크가 너무 큽니다. Shopify를 통해 검증된 Payment Gateway와 Inventory System을 활용하여 개발 속도와 안정성을 동시에 확보합니다. |
| **검색 시스템** (Discoverability) | 상품 검색과 필터링은 일반 DB 쿼리로 처리하기 매우 복잡하고 느립니다. | **Algolia API** | 실시간, 지연 없는 강력한 검색 경험(Search UX)을 제공하는 데는 Algolia가 업계 표준입니다. 초기 아키텍처에 반드시 포함해야 합니다. |

## ✨ [2단계] 핵심 기능 정의 및 모듈 분리 (Feature Breakdown)

모든 기능을 하나의 거대한 코드로 묶으려고 하면 유지보수성이 폭발적으로 떨어집니다. **모듈(Module)** 단위로 설계하고 API 게이트웨이를 통해 호출하는 것이 시니어 엔지니어의 관점입니다.

1.  **상품 카탈로그 모듈 (`/api/products`)**:
    *   필터링: (가격대, 카테고리, 색상) -> Algolia 검색 요청으로 처리.
    *   정렬: 최신순, 인기순 (Shopify API의 메타 필드를 활용).
    *   **핵심:** `ProductSlug` 기반의 고유 ID를 부여하고, 모든 페이지에서 이 Slug를 중심으로 데이터를 조회해야 합니다.

2.  **장바구니/구매 흐름 모듈 (`/api/cart`)**:
    *   사용자 인증: NextAuth.js와 연동하여 세션 기반으로 관리. (가장 중요)
    *   상태 관리: 장바구니는 클라이언트 측 상태(`useState`나 전역 스토어)로 임시 저장하고, 결제 직전에 **Shopify API**를 통해 서버에 트랜잭션을 요청해야 합니다.

3.  **결제 및 수익화 연동 모듈 (`/api/checkout`)**:
    *   **핵심:** 이 과정은 Shopify의 Checkout Flow가 담당하는 것이 가장 안전합니다.
    *   만약 PayPal을 *독립적으로* 통합하려면, **Webhook 리스너**를 별도로 구축해야 합니다. 즉, 고객이 결제를 완료하면 (Shopify/PayPal에서) 우리 서버로 `[PaymentSuccess]` 웹훅 신호가 와서, 이 신호를 받아 재고 차감 및 주문 확정 로직을 실행해야 합니다.

4.  **관리자 페이지 모듈**:
    *   사용할 필요가 없습니다. CMS(Strapi)와 커머스 엔진(Shopify)이 각각의 관리 기능을 담당하도록 분리합니다. 개발자가 직접 구축하면 기능 누락이나 보안 취약점이 발생하기 쉽습니다.

## 💰 [3단계] 수익화 연동 검토 (Monetization Integration Strategy)

**PayPal 통합 방안:**
우리가 목표로 하는 것은 단순한 결제 버튼 배치가 아닙니다. 우리가 가진 '워크플로우 솔루션 패키지'를 구매하는 경험을 제공해야 합니다.

1.  **구매 플로우 설계**: 고객이 웹사이트에서 컨설팅/패키지를 선택 → 장바구니에 담기 → **결제 단계 진입**.
2.  **Shopify 활용 원칙**: 상품 가격, 세금, 배송료 등은 Shopify의 트랜잭션 로직을 거치게 합니다.
3.  **PayPal 통합 지점 (Webhook)**: PayPal을 결제 옵션으로 제공받는 것은 쉽습니다. 그러나 **수익 모델 자체를 제어하는 방식**은 다음과 같습니다.
    *   `[판매 상품]`의 메타데이터에 '솔루션 컨설팅 팩'이라는 속성(Custom Property)을 부여합니다.
    *   고객이 결제 완료 후, Shopify가 우리 서버로 웹훅을 보내면, 서버는 이 `[속성 정보]`를 읽어와서 **사용자에게 맞춤형 온보딩 자료 (Lead Magnet)**를 제공하는 로직을 실행하게 합니다.

> 💡 **결론:** PayPal은 결제 수단으로 사용하고, 실제 수익 모델(솔루션 패키징)의 가치는 웹훅과 CMS가 관리하는 *정보*에 집중해야 합니다.

## 🚀 [4단계] MVP 구축 로드맵 제안 (Actionable Roadmap)

개발 리스크와 시장 검증 속도를 고려하여 **3단계 스프린트**로 분리합니다.

### Phase 0: 기획 및 환경 설정 (1주차)
*   **액션:** Next.js 프로젝트 초기화 (`web_init` 사용). Strapi/Contentful 계정 생성 및 기본 스키마 정의. Shopify 개발자 계정 생성 및 API 접근 권한 확보.
*   **검증 목표:** 데이터 플로우(Strapi → Next.js)가 정상적으로 작동하는지 확인.

### Phase 1: MVP (Minimum Viable Product) 구축 (2~3주차)
*   **핵심 기능:** 상품 목록 조회, 단일 상세 페이지 보기, 장바구니 임시 저장, 테스트 결제 흐름(Shopify API 연동).
*   **엔지니어링 초점:** 데이터 구조 확립 및 기본적인 성능 측정. (SSR/SSG 구현 확인)
*   **결과물:** 실제 상품 몇 개를 등록하고 구매까지는 가능하지만, 복잡한 워크플로우는 제외된 최소한의 판매 사이트.

### Phase 2: 고도화 및 수익 모델 통합 (4주차~)
*   **핵심 기능:** Algolia 검색 연동, 웹훅 기반 맞춤형 온보딩 자료 자동 배포(솔루션 패키징), 사용자 리뷰 시스템 추가.
*   **엔지니어링 초점:** 트랜잭션의 신뢰성 확보 (에러 핸들링, 재시도 로직 구현). PayPal/결제 수단 다양화.
